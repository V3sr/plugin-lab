# Portfolio and GitHub evidence

## Current honest description

**Plugin Lab — product discovery and architecture, September 2026**

Researched the current ChatGPT/Codex plugin system, compared competing integrations and designed a permission-aware Discord event/handoff assistant with a validation and distribution plan.

This describes the current planning deliverable. Do not yet claim that the service was built, deployed, approved, tested with users, or used by communities.

## Stronger bullets after implementation

- Built an authenticated MCP service that generated source-backed event briefs for **[N] consenting teams**, with **[X]% four-week human retention**.
- Implemented requester-specific channel authorization and revocation handling; verified **[N] permission and cross-tenant cases** with **[measured result]**.
- Evaluated **[N] representative tasks** and improved **[specific metric]** from **[A] to [B]**, while reducing p95 response time to **[measured duration]**.
- Shipped a reproducible open-source package and independently documented onboarding; reduced median setup time from **[A] to [B]** in **[N] observed installs**.

Replace every placeholder with measured evidence or omit that clause. Do not equate a server's members with users. If self-hosted users cannot be measured responsibly, report independently verified installations instead of guessing.

## Repository workflow

Keep the default branch readable and current. Start each implementation milestone with a linked issue, work on a branch, and merge a small reviewed PR. Tag actual usable releases. Add a changelog when there are releases to describe. Keep research plans separate from achieved results.

Commit messages should name meaningful changes. Keep real timestamps; no empty commits, fabricated feature chronology or retroactive backdating. Verify account attribution on the first remote commit. The contribution calendar is secondary to demonstrable work; visibility and GitHub's counting rules affect it.

## Suggested demo

Use a fully synthetic club event with changing times, a room-booking proposal, one accepted responsibility and one unresolved task. Show the useful result, then one denied private-channel request and a role-revocation test. Explain the limits in a few clear sentences. A two-minute demo with inspectable evidence is enough.

## Release-readiness narrative

When the project is ready for a resume, link the repository, a functioning permitted demo/install route, architecture, evaluations and a measured case study. Explain what the founder implemented and how external APIs/models were used. A store listing is an additional artifact, not a substitute for technical or adoption evidence.
